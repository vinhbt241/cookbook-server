# The admin dashboard is an in-repo HTML namespace, gated by a role enum and Pundit

The server is a bearer-token JSON API with no HTML surface, but admins need to Curate `Ingredient`s, Moderate the shared `OriginalRecipe` cache, and monitor `RecipeImport`s. The dashboard is an `Admin::` controller/views namespace in this same app (cookie session + CSRF scoped to admin controllers), admins are a `role` enum on `users` (the first one seeded with a password) rather than a separate credential system, and authorization goes through Pundit with a base policy encoding `admin?`.

**Considered options**: a separate admin app calling admin JSON endpoints was rejected because the data and domain logic already live here and a second app would only render tables. A disjoint `Admin` model was rejected in favor of a role enum so admins reuse the existing identity/session stack and can be managed from the dashboard itself. Hand-rolled `admin?` checks were rejected in favor of Pundit because the permission model is expected to grow (user management is deferred, not dead) and retrofitting authorization later is costlier than adopting it now. Re-parse overwrites the cached `OriginalRecipe` in place (keeping import history) rather than deleting it and hoping a user re-triggers; Ingredient deletion is a soft `Deactivate` rather than a hard delete because historical `Match`es reference the row.
